Practice 6 AI usage log

Tool: Claude Code (Claude Opus 5.5) in the T3 Code app.

User requests that directed the work:
- Read the Practice 6 sheet and explain the tasks and what has to be created.
- Design the test suite before any code: which edge cases structs and
  functions introduce, what must be covered, what the fixture files must look
  like, and how many tests give real coverage without dead weight.
- Create the practice-6 branch, write the tests and the implementation,
  commit after each finished and tested step, and report what was added and
  how it was verified. Do not push.

Use and review:
- Test design came first. Claude listed the edge cases (field index
  correctness with mixed field types, value semantics of copies, parameters
  and results, the one-value copy versus the one-field struct, deep mut on a
  whole-object :=, forward and mutual calls, top-level isolation, the runtime
  name clash, the program order) and proposed 12 tests/ok and 11 tests/err
  programs: the six of each named on the sheet, the three sheet examples
  verbatim, and a few where the rule is subtle. The smaller cases became one
  line each in the existing unittest tables instead of separate fixtures.
- The user accepted the proposed decisions: a wrong number of values is
  reported at the '{', an unknown field at the field name, a const link at
  the start of the chain naming the link, a wrong argument count at the
  function name, a wrong exit type at the exit operand; a variable may not
  take a function's name; an i32 exit in an i64 function widens; structs
  cannot be compared with == or !=.
- Every expected result and line:column was worked out by hand before the
  first run; all 23 fixtures and all new unittest positions matched.
- Tasks 1-3 (one commit, because a struct can only be observed through the
  '.' of Task 3 and a function through its call): new tokens struct, fn, '.',
  ',', '(', ')', '->'; Struct, FieldDecl, Fn, Param, Init, Field and Call
  nodes; the fixed program order in the parser; a struct table, a
  signature pass before any body, a separate scope stack per body and the
  mut-chain rules in the checker; named struct types, gep by index,
  prefixed functions ("fn."), parameter slots in each entry block, ret and
  call in the code generator.
- Changed on purpose after the first draft: two messages were made more
  precise than "used before its declaration" and "it is not mut":
  "variable 'base' is not visible inside function 'bump'" and
  "cannot assign to 'n': 'n' is a parameter".
- The first version of an IR unit test parsed the module back with
  llvmlite.binding and compared names, but LLVM renames types on reparse
  (%Point.7); the test now checks the emitted str(module) text.
- Additional task (its own commit): nested {} through the same check as the
  outer {}, built with insertvalue. While restoring it, an inner {p} copy
  (allowed, since the inner {} has the outer rules) crashed the code
  generator; it was fixed and a unit test runs that program through lli.
- Mutation checks: each of these deliberate bugs made a named fixture fail -
  every gep at index 0, no function prefix, no deep-mut check on :=, no
  check of the links of a chain, no i32 to i64 argument widening, and a
  body that sees the top-level scope.
- Verified both on macOS (LLVM 22) and in the Ubuntu 24.04 VM (LLVM 18,
  llvmlite 0.49):
  - python3 check.py passes 113/113, including the Practice 2-5 fixtures and
    46 unit tests (with the opt mem2reg check in the VM).
  - opt -passes=verify accepts every tests/ok program.
  - lli prints true, 55, 28 and 36 for the sheet programs, and
    full_compiler.sh builds and runs them natively.

The compiler still builds every instruction through llvmlite.ir, and IR text
exists only as str(module).
